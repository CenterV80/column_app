User ⇄ Claude ・ 開発チャットログ

01そもそもComfyUI、いる?
簡単な画像生成のシステムならComfyUIすらいらないんじゃない?モデル決め打ちなら。
その通り。txt2img/img2imgだけでLoRA構成も固定でいいなら、diffusers直叩き+軽量APIで十分です。
02作るものを決める
キャラシートからポーズ違い画像を3x2レイアウトで出すだけのツール作りたい。モデルはFluxとか何でもいい。
Flux Kontext(キャラ一貫性重視)か SDXL+ControlNet OpenPose の二択ですね。6ポーズ推論してPILで3x2合成、で進めます。
03棒人間エディタ、爆誕
ポーズ指定はテキストだけ?骨格で厳密指定する?
いるかも。あと棒人間描くエディタも入れたい。
了解、OpenPose確定ですね。既存の openpose-editor を流用します?それともCanvas自作?
Canvasの方が手軽だよね。
Canvas自作で進めます。ちなみにこれ、ComfyUI WebUIのプロジェクトとは別物?
はい、全く別のプロジェクトです。
新規プロジェクトとして認識しました。名前、仮決めしましょうか。
sample image maker でどうですか?
「sample-image-maker」命名完了。
04まずバックエンドから
次はフロントとバックエンド、どちらから攻めます?
バックエンから。
FastAPI + diffusers構成でいきましょう。/generate(6ポーズ推論→3x2合成)と/presetsのAPI案を用意します。
05GPU問題、そしてモデル沼
GPU環境は?
GPU環境は会社のRTX5080です。あともう一台、RTX4070Tiも。
5080(16GB)と4070Ti(12GB)、それぞれで動く構成を整理しますね。本番稼働はどっちのマシン?
使うのは5080ですが、古いマシンでも動くような構成にしたいです。
では4070Ti基準で選定しましょう。Flux Kontextは量子化必須、SDXL+ControlNetなら量子化なしで収まりやすいです。
すいません、まず必要なモデルとその容量を確認したいです。
Web検索実施
Flux Kontext:フル約24GB / fp8約12GB / GGUF Q8約12.8GB / GGUF Q4約7GB。対して SDXL+ControlNet OpenPoseは合計約9.3GB。後者が4070Tiに無理なく収まりますね。
テキストエンコーダーはどうなりますか?
SDXLはCLIP ViT-LとOpenCLIP ViT-bigG、2つのテキストエンコーダーを使用します。どちらもSDXL baseのcheckpointファイルに内包されているので、別途ダウンロード・容量計算は不要です(先ほどの合計約9.3GBにすでに含まれています)。
06量子化沼にハマる
fp8量子化とGGUF Q8の違いは?
fp8はTensorコアでネイティブ高速演算、GGUF Q8は整数量子化で専用ローダーが必要、という違いです(比較表つきで整理)。
pruned版はないの?
pruned文化はSD1.5世代のもの。SDXL/Flux世代は元々軽量な配布なので、あまり存在しません。
pruned は古いやり方なのですか?
「古い」というより、削る対象自体がもう配布物に含まれなくなった感じです。軽量化の主流はpruning→quantizationに移りました。
話を戻してSDXL+ControlNetでお願いします。
確定です。SDXL+ControlNet OpenPose、合計約9.3GBで5080・4070Ti両対応。
07API設計とモデル管理
次はAPI詳細、それともフロント?
バックエンドAPIの詳細。
POST /generate(キャラシート・6ポーズ・プロンプト等→合成画像・個別画像・seed・生成時間)、GET /presets、GET /healthを用意しました。
モデルも含めてパッケージにしますか?
いえ、モデルは同梱しない方がいいです。ボリュームマウント等で分離、イメージ肥大化を防げます。運用はDocker?venv?
モデルはStability Matrixのフォルダ階層から取ってくるようにしたいです。
Stability Matrix標準構成(Models/StableDiffusion, VAE, ControlNet…)に沿ってパス解決しましょう。固定ファイル名指定?自動検出?
model内のフォルダ階層を自動、は良いと思う。
find_model_file関数で自動検出します。複数ファイルが見つかった場合はどうします?
複数はエラーでいいと思います。
確定、複数該当時はエラーで起動停止。

サンプル画像を簡易に作るのが目的なので6ポーズ同時で。
3x2グリッドで6セル同時編集ですね。想定ウィンドウサイズは?
横は1980pでいいんじゃないですか。

出力サイズは可変で。個別出力にも対応してください。
width/heightパラメータ追加しました。ダウンロードボタン、ZIP一括ダウンロードも要ります?

すいません、デスクトップアプリ前提で話してました。
前提の大幅修正

ではPySide6(LGPLで扱いやすい)+ QGraphicsView/Sceneで棒人間エディタ、diffusers直接呼び出し、QThreadで非同期処理にします。これまでのAPI設計は関数分割としてそのまま流用できますよ。
はい。

この会話から学べること

  • 1「ComfyUIいらなくない?」の思いつきが、最終的にはPySide6のデスクトップアプリという全然違う形に着地する。バイブコーディングは最初の一言と最終形が一致しなくて当然。
  • 2「すいません、実は前提が違いました」は普通に起こる(フェーズ08参照)。その都度AIが方針転換して整理し直してくれるので、思いついた順に話して大丈夫。
  • 3会話は寄り道・沼(fp8 vs GGUF vs pruned)をしながら進む。最後にちゃんと仕様書という1つのドキュメントに落とし込むところまでが一区切り。

追記:実際にやってみての気づき

  • 1アプリの形態(Webアプリかデスクトップアプリか)は、一番最初に伝えておくべき情報だった。今回はフロントエンドの設計がある程度進んだ段階で発覚し、技術スタックの選定からやり直す羽目になった(フェーズ08)。
  • 2使用言語をPythonに固定する、という指示も冒頭で出しておくと良い。バックエンドからGUIまでPythonで完結させれば、依存ライブラリの管理がぐっとシンプルになる。
  • 3ログ出力(デバッグパネル)は後から足す機能ではなく、最初から組み込んでおきたいもの。動かして不具合が出たときにAIへ状況を正確に伝える手がかりになるので、実質必須の機能だと感じた。
  • 4疑問に思ったことは遠慮せずどんどん質問するのがコツ。fp8とGGUFの違いやpruned版の有無など、細かい点をその場で確認しながら進めたことで、後工程の手戻りを防げた。
