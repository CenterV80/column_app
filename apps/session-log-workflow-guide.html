🤖 セッションログ運用ワークフロー

GitHub Copilotなど、LLMとのコーディング作業の知見を蓄積・再利用するための運用ルール

LLMとのコーディング作業は、セッションが終わるとその場の気づきや躓きポイントが消えてしまいがち。 このワークフローは「やったこと・気づき・躓いた点と対処法」をファイルに蓄積し、 次回セッションで読み込んで再利用できるようにする運用ルールです。以下はそのままコピペして 使えるテンプレート集です。

📁 ファイル構成

まず、この4つのファイルを用意します。
docs/ session-log.md # 直近の作業ログ（詳細） session-log-archive.md # 古いログの要約アーカイブ known-issues.md # エラーパターン → 対処法のナレッジベース .github/ copilot-instructions.md # 常時読み込まれるルール定義

⏱️ 書く／読むタイミング

書くタイミング

タイミング 内容
問題を解決した直後 躓いた点→原因→対処を1エントリ追記
作業がひと区切り（コミット前） やったことを1〜2行で追記
同じエラーに複数回遭遇 known-issues.md にも別途追記
  • ❌ 1日の終わりにまとめて書く（詳細が抜ける）
  • ❌ 変更のたびに書く（ノイズが多い）
  • ✅ タスク単位・問題解決単位で都度書く

読むタイミング

タイミング 読む対象
新しいセッション開始時 session-log.md の直近5〜10件
プロジェクト切り替え時 該当プロジェクトのログのみ
同一セッション継続中 読み直し不要（既にコンテキストにある）

📝 ログのフォーマット

テンプレ
docs/session-log.md に追記する1エントリ分
## [日付] [作業タイトル] - やったこと: （1〜2行で） - 気づき: （次回に活きる発見。無ければ省略可） - 躓いた点 → 原因 → 対処: - 問題: - 原因: - 対処: - 次回への申し送り: （あれば）
ポイント： 自由記述にすると質にばらつきが出るので、このフォーマットを固定して使うのがコツです。

⚙️ copilot-instructions.md に仕込むルール

テンプレ
.github/copilot-instructions.md に追記する内容
## 作業ログのルール - 一つの問題を解決した、または一区切りの作業が完了したタイミングで、 `docs/session-log.md` の末尾に指定フォーマットで追記すること。 - 追記前に必ずファイルの既存内容を確認し、重複した内容は書かないこと。 - 些細な変更（タイポ修正、フォーマット調整など）は記録しない。 - 同じエラーパターンに繰り返し遭遇した場合は `docs/known-issues.md` にも 「エラーパターン → 対処法」の形で追記する。

セッション開始時に打つプロンプト

テンプレ
docs/session-log.md の直近10件と docs/known-issues.md を読んでから作業を始めて。 今日やるのは○○です。
VS Code拡張の場合： @workspace docs/session-log.md を踏まえて、○○を実装したい

月1ペースでの圧縮プロンプト

テンプレ
docs/session-log.md の中で1ヶ月以上前のエントリを、 「日付範囲 / 主なテーマ / 得られた知見」の3行程度に要約して docs/session-log-archive.md に移し、元のファイルからは削除して。 直近1ヶ月分のエントリはそのまま残すこと。

💡 設計のコツ

  • トリガーを具体的にする：「適宜書いて」ではなく「解決した瞬間」「コミット前」など明示する
  • フォーマットを固定する：自由記述だと質にばらつきが出て検索・要約しづらい
  • 重複防止を指示に含める：「読め」だけでなく「読んで既存内容と重複しないか確認しろ」まで書く
  • 肥大化対策を最初から組み込む：全件読ませるのではなく「直近だけ読む＋古いものは圧縮」する仕組みにする

🔍 コンテキストとの関係（補足）

このワークフローの前提として、以下の点を理解しておくと運用がぶれません。
  • コンテキストは「毎回組み立てて渡す入力データ」であり、LLMが自発的に記憶しているものではない
  • session-log.md を読ませる行為は、人間またはツール側が明示的にファイル内容をコンテキストへ組み込む操作
  • MCP経由であればLLM自身がツールを呼んで能動的にログを取得することも可能（ただしそれも「ツールを呼ぶ」という明示的な行動が必要）
